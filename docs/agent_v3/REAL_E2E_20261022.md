# v3 真实端到端测试（含真实视频）· 2026-10-22

执行与审读：Claude。授权：用户于 2026-10-22 明确要求“撰写几个高质量真实任务，使用 v3 模式完成测试，总时长不超过 60s，画质不用太高，尽量选用 wan2.7 模型”（D-061，属 D-030 的一次性例外）。

## 结论

**v3 的规划、审批、预览、选择与单段生成在真实服务商上能走通，成片质量可用；但发现两个会让真实用户直接失败的阻塞缺陷，以及一个高概率触发的模型偏好缺陷。默认开启 v3 前必须修复。** 这三项在此前所有 Mock 评测中都无法暴露。

| # | 严重度 | 问题 | 影响 |
|---|---|---|---|
| F1 | **阻塞** | 真实 wan2.7 视频不带 SAR 标记，探测结果为 `geometry_unverified`；用户指定了比例时，compose 一律报 `INVALID_SOURCE`（`plans/aspect.py:54`） | 所有指定比例的多镜头成片在拼接步骤失败，此前的生成费用已花掉 |
| F2 | **阻塞** | 默认文生图模型 wan2.6-image 的默认参数与适配器都带 `enable_interleave: true`，服务商忽略 `n=1`，每次返回 5 张；运行时正确报 `PLAN_OUTPUT_COUNT_MISMATCH` 并停止 | v3 默认图片路径在真实环境下每次都失败，且实际计费为 5 倍；该参数不在参数 Schema 中，Agent 无法关闭 |
| F3 | 高 | V11d 要求“偏好逐字保留用户原文”，brief 存成整句（如“图片使用wan2.7-image模型”）；`agent/model_selection.py` 只剥掉末尾的“系列/模型”，无法解析整句，偏好匹配不到任何模型，被归入视频约束 | 用户在句子里点名模型时（本轮 3/3 次），i2v 候选为空、文生图退回默认模型；一次 Agent 直接放弃任务 |
| F4 | 中 | 系列偏好（“wan2.7系列”）因系列内含视频模型而只约束视频；图片节点在没有图片级偏好时只允许服务器默认模型。Patch 不能修改 brief | “全部用 wan2.7”到不了图片；默认图片模型失败后，无法通过修改换模型（T2 死路） |
| F5 | 中 | 规划质量：“两镜头短片”首版规划为两段分别交付、无 compose，且两个镜头共用同一张首帧 | 用户提出修改后修正；Director/Skill 应默认把多镜头短片拼成一个成片 |
| F6 | 已修 | 真实实测时长 8.03 / 5.04 / 10.03 秒，印证 V13e（已合并，D-060）的必要性 | exact 模式此前会误判 |

正面结果：
- 规划层：每个付费步骤都等审批；模型不可用时 Agent **提问而不是静默换模型**（4 次）；修改意见都被正确落实（T1 改 t2v、T3b 加拼接与独立关键帧）。
- 约束：比例与时长都正确落到参数（16:9→1280×720，9:16→720×1280；约 8 秒→5–11 秒）。
- 选择门：三张不同风格的真实图片、人工选择、图生视频全链路成功。
- 身份一致性：T3b 两个镜头中小狐狸的外形（红色针织围巾、毛色）保持一致。
- 生成速度：wan2.7-t2v 8 秒约 4 分钟；wan2.7-image 三张约 70 秒；wan2.7-i2v 两段 10 秒合计约 2 分钟。

## 用量

- 真实视频：4 段，共 **33 秒**（上限 60 秒），全部 wan2.7（t2v 1 段、i2v 3 段），720P。
- 真实图片：请求 8 次；**实际生成 20 张**（T2 的 wan2.6-image 交错输出 15 张；wan2.7-image 共 5 张：T2b 三张、T3b 定妆图与第二镜关键帧各一张）。执行器的图片上限按请求的 n 计数，未能拦住服务商多返回的图片，报告以实际张数为准。
- 文本/视觉：5 个 Run 共 75 轮规划 LLM（deepseek-v4.1-flash），无多模态理解调用。
- 演示 credits 不是实际账单；实际费用以 DashScope 控制台为准。

## 隔离与安全

- 执行器 `backend/scripts/v3_eval/real_e2e.py`：复用 `safety.configure_environment`（禁用 dotenv 自动加载、仅白名单读取 DashScope 凭据、不解析 MySQL/Redis），临时 SQLite 与存储（`%TEMP%/cinecrew-real-e2e-20261022`），MQ 关闭，未修改任何 .env。
- 在独立 worktree 上运行已合并的 `feat/agent-v2` 代码，未触碰 Codex 工作区。
- 媒体硬上限在请求发出前预留：视频总秒数 ≤60、仅 wan2.7 视频模型、图片 ≤14（按请求 n）；事前离线验证三道上限均在发请求前拦截。
- 所有付费步骤（计划批准、预览门、选择门、结果批准）都由我逐一审阅后手动执行。

## 建议的修复（交 Codex，默认开启前完成）

- **F1**：对本系统生成适配器产出的视频，缺失 SAR 标记按方形像素（1:1）处理并记录来源依据；用户上传等外部来源仍保持保守校验。V12a 中“给 Mock 视频加 setsar=1”的修正应改为让 Mock 与真实输出一致（不带 SAR），并补回归：无 SAR 的真实形态视频在指定比例下能拼接。
- **F2**：agent 计划中的图片节点对 wan2.6-image 等 `dashscope_image` 模型显式发送 `enable_interleave=false`（或将该默认值改为 false，需确认经典工作流的首帧节点是否依赖多图）；运行时按实际返回张数记账；补测试。
- **F3**：brief 中模型偏好分开存 `selector`（模型 ID 或系列名）与 `source_text`（原文）；或让 `model_selection` 复用 `model_policy` 的选择器提取。补测试：“图片使用wan2.7-image模型”“全部使用wan2.7系列模型”都能正确匹配。
- **F4**：决定“系列偏好是否同时约束图片”（建议：系列内有图片模型时也约束图片节点）；允许经用户确认的修改更新 brief 中的模型约束，或在 Patch 流程中给出明确出路。
- **F5**：Director 提示词与 long-form-video Skill：多镜头短片默认 compose 成一个成片，各镜头首帧应各自对应画面。

修复后可用剩余授权（视频约 27 秒）复跑 T3b 并补测局部修改。
