# 下一步决策：先推进 Phase 4，纳入可靠执行审计

结论：下一步优先进行重构说明书中的 **Phase 4：稳定性与系统评估**。把消息队列方案的 Phase 0 只读审计作为 Phase 4 的执行可靠性工作项；依据故障注入和负载数据决定可靠队列的实现顺序，不直接一次性切换 Redis Streams。

## 当前仓库证据

| 现状 | 代码依据 | 对下一步的影响 |
|---|---|---|
| Agent 已使用独立 worker、持久化 checkpoint 和工具账本 | `app/agent/worker.py`、`recovery.py`、`docker-compose.yml` | MQ 应承担底层执行分发，继续保留 LangGraph 的规划、审批和恢复职责 |
| Job 队列是进程内 deque，运行记录使用线程对象 | `app/services/job_queue_service.py:JobQueueService` | 不具备多进程共享的可靠分发，需要审计进程退出与重新领取语义 |
| Poll 在节点内反复查询并 sleep | `app/services/node_runner.py:_poll_until_complete` | 等待占用执行线程；负载评估应测队列积压、线程数和等待延迟 |
| 获取结果、下载、压缩、工件登记仍串联执行 | `app/services/node_runner.py:_complete_task_from_adapter` | 下载故障与生成状态耦合，需明确提交未知、待下载和可恢复状态 |
| 本次付费失败源于规划语义和审批前终止 | Phase 3 付费记录 | 更换消息传输组件不能直接解决该类失败，先建立任务完成率与人工修正指标 |

消息队列说明书的总体方向合理：Submit/Download 事件驱动，Poll 按到期时间调度，业务状态以 MySQL 为准，Outbox 保证可靠投递，未知提交结果禁止盲目重发。文档中“暂不引入 LangGraph”属于编写时的背景，需要更新为“保留已存在的 LangGraph，不让队列重新实现 Agent 编排”。

## 推荐执行顺序

1. **Phase 4 基线与评估**：固定经典流程、从零创作、原片二创的评估集。记录完成率、成本、耗时、人工修改次数，以及范围/时长/模型约束正确率；用 Fake Provider 做并发和故障注入。
2. **恢复与发布门槛**：覆盖 checkpoint 前后崩溃、模型接收后响应丢失、下载失败、重复审批和部分成功。建立可观测日志、暂停开关、灰度及回滚验证。未知付费结果必须可见且不得自动重复提交。
3. **MQ Phase 0 审计**：将 `ApiTask`、`ToolInvocation`、Job/DAG、工件和现有事务映射到方案状态机，列出同步图片接口、存储依赖、租约及幂等键。避免平行新建一套任务事实来源。
4. **按审计结果分阶段落地**：需要多 worker、多主机、重启后可靠分发，或确认轮询/下载占用影响吞吐时，优先实施 Outbox 与阶段化执行，再逐步切换 Streams。每阶段独立迁移、故障验收、feature flag 与回滚。

这不是将可靠队列无限延期。当前进程内队列不能作为已具备分布式可靠性的依据；面向多进程/多主机正式发布前，必须完成持久化任务分发及恢复验收。低并发单 worker 的 Phase 4 评估可以先开展，无需先完成整套 MQ 改造。

本次仅作代码审计与路线判断，没有部署 Redis，也未修改现有调度架构。
