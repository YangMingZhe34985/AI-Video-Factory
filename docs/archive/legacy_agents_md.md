# CineCrew（原AI Video Factory） — 代码开发规范

## 1. 核心原则

- **根因优先**：出现 Bug 时，先分析根本原因，再修改代码。禁止仅针对当前失败样例添加特殊判断、硬编码或绕过逻辑。
- **简单优先**：优先采用简单、清晰、可维护的实现，避免过度设计和不必要的抽象。
- **最小改动**：只修改解决当前问题所必需的代码，避免无关重构和扩大修改范围。
- **复用优先**：优先复用已有模块与通用机制，避免重复实现相似功能。

## 2. 代码质量

- 遵循项目现有的目录结构、命名规范、架构分层和技术栈。
- 保持函数职责单一，避免过长函数、重复逻辑和不必要的嵌套。
- 不随意增加配置项、状态变量、兼容分支及抽象层。
- 不通过堆积 `if/else`、`try/except`、重试逻辑和兜底返回值掩盖设计缺陷。
- 必要的输入校验、异常处理、权限约束和安全检查必须保留，但应放在合理的统一边界。

## 3. Bug 修复规范

修复 Bug 必须遵循以下流程：

1. **定位**：复现问题，分析调用链、数据流和错误原因。
2. **设计**：判断是否存在更通用的修复方式，优先修正错误的设计或实现。
3. **修改**：使用尽可能简单的方案解决问题，避免针对单一案例特化。
4. **验证**：验证原问题已解决，且相关正常功能没有回归。
5. **清理**：删除修复过程中产生的临时代码、无效判断和冗余逻辑。

如果多次修复仍然失败，应重新分析根因，而不是继续叠加补丁。

## 4. 架构约束

- 保持前后端分离、模块职责清晰，避免跨层调用和不必要的模块耦合。
- 工作流调度、DAG 依赖管理、节点执行和模型调用应保持明确的职责边界。
- 通用问题应在公共机制中解决，不应在多个工作流节点中重复添加相同防护逻辑。
- 不得为了修复局部问题，破坏已有工作流的调度、并行执行、局部重跑和故障隔离语义。

## 5. 验证与交付

- 修复 Bug 时，优先补充能够复现根因的回归测试，而不是为当前实现凑测试。
- 优先运行相关测试；涉及公共逻辑时，扩大验证范围。
- 不得为了让测试通过而削弱断言、跳过失败测试或修改测试以迎合错误行为。
- 每次开发结束，简要说明：**修改内容、根因、验证结果和遗留风险**。未验证的内容必须明确标注。

## 6. 最终要求

**代码质量优先于局部测试通过率，长期可维护性优先于短期修复速度。**

遇到问题时，先判断是否需要修正现有设计，而不是默认增加新的防御代码。

**一个正确的通用修复，优于十个针对特定场景的补丁。**
